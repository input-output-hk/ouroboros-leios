tx-centrifuge

The load generator, a closed-loop driver. A workload is a self-contained circuit: its own disjoint partition of funds, single-use UTxOs, its own builder turning funds into transactions, its own token-bucket rate limit, its own injection targets and its own observer following the chain. Every transaction spends funds and creates outputs, and an output becomes spendable again only once that workload's observer has seen its transaction reach the confirmation depth, so the transactions form chains gated by the chain itself and the funds budget is the buffer bridging confirmation latency. With on_exhaustion = error, a workload that cannot recycle funds as fast as it spends them runs that buffer to zero and fails the run rather than quietly slowing down.

  • 51 workloads and 51 observers, one of each per pool: every workload drives its own pool and no other (51 of 51), and its observer follows that same pool rather than a shared one (51 of 51)
  • builder value, every transaction 1-in 1-out with 1 destination signing key per builder, fee 1,000,000
  • rate limit: token_bucket, scope per_target, at 3.40 tx/s per target, 173.6 tx/s offered in aggregate (34.71 KB/s at the 200 B measured transaction size)
  • recycling on_confirm at confirmation depth 3, over a nodetonode observer
  • initial funds from genesis-funds (genesis_utxo_keys), scope per_workload, so a fund returned by a workload can only be taken up by that same workload
  • on_exhaustion = error · max_batch_size = 0

The generator runs on the explorer machine in eu-central-1, which forges nothing, so every transaction crosses the network before the pool that must place it in a block ever sees it: the round trip a workload pays is the EU row for its target's region in the table above. Each workload holds two buffers of its own, funds waiting to be built and built transactions waiting to be delivered.

2. Propagation, fetching the EB references

Three instants are used:

  • The forger forges the endorser block (Consensus.LeiosKernel.BlockForged)
  • The forger announces it over the network (LeiosNotify.Remote.Send.BlockAnnouncement)
  • A peer finishes receiving the endorser block's bytes over the network (LeiosFetch.Remote.Receive.Block)

Endorser blocks whose hash was forged more than once, and so referenced by more than one ranking block, are left out of this section.

3. Acquiring, the EB written down

A delivered endorser block is not yet held: until its write is durable the body still reads as not-held, which is why the same endorser block can be fetched again meanwhile. Consensus.LeiosKernel.BlockAcquired is the moment that ends: the node has the reference list stored and claims to hold it, registering which referenced transactions it still needs. This is the step from arrival to that claim, which includes waiting for the single writer, and how often the same endorser block was stored again.

6. Forks

Every switch a node made off a chain it already had, one row per node and switch (ChainDB.AddBlockEvent.SwitchedToAFork). A contest is one pair of tips, so a contest the whole cluster lived through counts once. Both rates below are contests per 1,000 blocks on the chain, so runs of different length compare directly.

The slot rate is the control and the height rate is the signal: two leaders in one slot is fixed by activeSlotsCoeff and cannot be engineered away, while a height battle is a node forging on a parent a sibling already had, which is propagation losing a race and is free to move. Reading the height rate without the control beside it cannot tell a propagation regression from a run that simply drew more forks.
